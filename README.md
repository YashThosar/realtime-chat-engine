# Realtime Chat Engine

A real-time chat backend built with **FastAPI, WebSockets, PostgreSQL and Redis Pub/Sub**.
Users sign up, log in, join rooms, and messages reach everyone in the room instantly.
The design focus is **reliability**: messages are ordered per room, duplicate-safe on retry, and can be delivered across more than one server instance.

## Features

- **JWT authentication** with bcrypt password hashing (signup, login, protected routes)
- **Rooms**: create, list, join, and view members, with membership checks on every room action
- **Real-time messaging over WebSockets**, with the JWT verified when the connection is opened
- **Per-room sequence numbers (`seq`)**: every message gets the next number in its room, enforced by a database unique constraint
- **Idempotent delivery**: each message carries a client-generated `client_msg_id`; a retried request returns the original message instead of creating a duplicate
- **Replay support**: `GET /rooms/{id}/messages?after_seq=N` returns only messages newer than the last one a client saw
- **Multi-instance delivery** with Redis Pub/Sub: a message published by one server instance reaches clients connected to another
- **Fully async data layer**: SQLAlchemy 2.0 async ORM with `asyncpg`, so database calls do not block the event loop
- **Schema migrations** with Alembic

## Architecture

```
 Client A ──WebSocket──►  Server 1 ──┐                         ┌──► Server 1 ──► Clients on Server 1
                                      ├─► PostgreSQL (save, seq)│
 Client B ──WebSocket──►  Server 2 ──┘                         │
                                      └─► Redis PUBLISH room:<id> ──► Server 2 ──► Clients on Server 2
```

### Message flow

1. A client sends `{"content": "...", "client_msg_id": "..."}` over its WebSocket.
2. The server checks whether this `client_msg_id` already exists in the room. If it does, the original message is reused.
3. Otherwise it assigns the next `seq` for the room and saves the message in PostgreSQL.
4. The server publishes the saved message to the Redis channel `room:<room_id>`.
5. **Every** server instance runs a subscriber on `room:*`. Each one forwards the message to the WebSocket connections it holds for that room.

PostgreSQL is the source of truth. Redis Pub/Sub is fire-and-forget, so a client that missed a live message catches up through the `after_seq` history endpoint.

## Data model

| Table | Purpose | Notable constraints |
|---|---|---|
| `users` | Accounts | unique `username`, unique `email`; stores a bcrypt hash, never the password |
| `rooms` | Chat rooms | references the creator |
| `room_members` | Which user is in which room (many-to-many) | unique `(room_id, user_id)` |
| `messages` | Chat messages | unique `(room_id, seq)` for ordering, unique `(room_id, client_msg_id)` for idempotency |

IDs are UUIDs, generated by the application, so multiple server instances never need to coordinate to create them.

## API reference

All routes except signup, login and health require `Authorization: Bearer <token>`.

| Method | Path | Description |
|---|---|---|
| POST | `/auth/signup` | Create an account |
| POST | `/auth/login` | Returns an access token (valid for 60 minutes) |
| GET | `/auth/me` | Current user |
| POST | `/rooms` | Create a room (creator becomes a member) |
| GET | `/rooms` | Rooms you belong to |
| POST | `/rooms/{room_id}/join` | Join a room (safe to call twice) |
| GET | `/rooms/{room_id}/members` | Members (members only) |
| POST | `/rooms/{room_id}/messages` | Save a message (members only) |
| GET | `/rooms/{room_id}/messages?after_seq=0&limit=50` | History, oldest first, only messages after `after_seq` |
| GET | `/health` | Liveness check |

### WebSocket protocol

Connect to `ws://localhost:8000/ws/rooms/{room_id}?token=<jwt>`. The token is passed as a query parameter because browsers cannot set custom headers on a WebSocket handshake. Connections with an invalid token, or from a user who is not a member of the room, are rejected.

Client sends:

```json
{ "content": "hello", "client_msg_id": "any-unique-id-per-message" }
```

Server pushes to everyone in the room (including the sender):

```json
{
  "id": "…", "room_id": "…", "sender_id": "…",
  "content": "hello", "seq": 7, "created_at": "2026-10-20T10:06:51.473334"
}
```

On bad input the server replies with `{"error": "..."}`.

Quick test from a browser console:

```js
const ws = new WebSocket(`ws://localhost:8000/ws/rooms/${ROOM_ID}?token=${TOKEN}`);
ws.onmessage = (e) => console.log(e.data);
ws.onopen = () => ws.send(JSON.stringify({ content: "hi", client_msg_id: crypto.randomUUID() }));
```

## Getting started

Prerequisites: Python 3.11+, Docker Desktop, Git.

```bash
git clone https://github.com/YashThosar/realtime-chat-engine.git
cd realtime-chat-engine

python -m venv .venv
# Windows: .venv\Scripts\activate      macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt

docker compose up -d        # PostgreSQL and Redis
alembic upgrade head        # create the tables

uvicorn app.main:app --reload --reload-dir app
```

Open http://localhost:8000/docs for the interactive API docs.

Configuration is read from environment variables (see `.env.example`); sensible local defaults are built in. **Set a strong `SECRET_KEY` for anything other than local development.**

### Running two instances (multi-instance delivery)

```bash
uvicorn app.main:app --port 8000     # terminal 1
uvicorn app.main:app --port 8001     # terminal 2
```

Connect one client to each port, in the same room, with different users. A message sent through one appears on the other.

### Troubleshooting

- **`password authentication failed` or connection refused on port 5432**: another PostgreSQL (for example a Windows service) may already be using the port. Stop it, then run `docker compose down -v && docker compose up -d`.
- **WebSocket drops while editing files**: use `--reload-dir app` so only code changes restart the server.
- **Virtual environment errors after moving the project folder**: recreate `.venv`; virtual environments cannot be moved.

## Design decisions

- **Async everywhere in the data path.** All connections share one event loop, so a blocking database call would stall every connected user.
- **Sequence numbers instead of timestamps.** Per-room `seq` gives a total order decided by one database, unaffected by clock differences between servers. It also makes reconnect catch-up a simple "give me everything after N".
- **Idempotency at the database level.** The unique `(room_id, client_msg_id)` constraint is the safety net behind the application-level check, so even concurrent duplicate requests cannot create two messages.
- **Postgres first, then publish.** A message is stored before it is announced, so a failed or missed live delivery never loses data.
- **Redis Pub/Sub for fan-out.** It keeps instances decoupled and is low latency. The trade-off is that it does not store messages, which is why replay comes from PostgreSQL.

## Testing status

- The API, WebSocket flow and Redis delivery were verified manually with multiple simultaneous clients, including two server instances on different ports.
- Automated tests currently cover the health endpoint only. A fuller pytest suite is planned.
- No load testing has been done yet, so no throughput or latency figures are claimed.

## Known limitations

- Messages sent through the REST endpoint are stored but not pushed live; WebSocket is the real-time path.
- The JWT is checked when a WebSocket connects, not continuously. A connection stays open after the token expires.
- No heartbeat, automatic reconnect, rate limiting or per-connection backpressure yet.
- Redis is a single point of failure for live delivery (stored messages remain available through the history endpoint).
- The JWT travels in the WebSocket URL query string, which can appear in server logs; use TLS and short-lived tokens in production.
